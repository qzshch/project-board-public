# 负责人和继承 SE 操作指南

产品4增加“治理策略”“时间与效率”“测试与自动化”，资产页增加候选提炼。先选择项目默认light/standard/strict，再按每张任务当前scope_hash核定风险；小项目或模块内部低风险任务可免完整模块评审和独立报告。已知跨模块/接口至少标准，权限、持久化数据、生产、共享资产与未知影响采用严格要求。任务包可以批量评估，但高风险子任务不能被包名掩盖。

时间使用estimate记录乐观/通常/保守投入及依据，time_change明确作业、等待、暂停与结束；记录阶段、原因和返修标签。结束后time_complete确认完整性，经理可留痕校正。历史投入不从领取间隔推测；估算报表区分自然历时、总投入、等待、返修与治理成本，相似样本不足时不编造分位估计。

测试先登记不可变case与suite，再用test_plan关联当前任务范围。手工检验用manual_run明确实际观察；自动检查用run_request入队，由本机批准套件摘要的runner实际执行。一轮可验证多张卡，提交引用test_runs，标准/严格交付不能仅写“测试通过”；轻量任务可用有依据的差异/预览核对，不为可逆小改动新写无意义测试。非代码任务可用产物锚点代替Git实现提交。

资产从candidate提议，经refine去耦、validate关联实跑与真实字节SHA、promote登记私有版本后才审核共享。复用后记录接入成本、预估节省及问题，两者不混算。详见[完整操作API](/help/operations)、[执行器指南](/help/runner)和[可填写模板](/help/templates)。这些操作均可使用客户端prepare-operations冻结请求并保存回执。

正式入口：http://example-server.example-tailnet.ts.net:18785 。服务及运行状态在 server，旧 PC 地址已停用。本文可以交给没有聊天历史的其他会话；不包含管理员入口、密钥或任何项目快照。

## 1. 新建项目与取得职责

先填写[项目初始化模板](/templates/project-init.json)，交由实例管理员创建独立空项目，并签发本项目 owner 身份。项目 ID、公告板网页地址、代码仓库目录是不同概念。项目 owner 不能创建全局身份或枚举其他项目。

实例管理员在自己的管理会话完成创建；全局运维说明仅向管理员会话开放。负责人只接受自己项目的身份文件。已有身份迁移到 server 时，保留 token、actor、project_id，只更新 url；旧 connect_ip 改为 100.64.0.10，不重新注册。

负责人用项目身份读取 `/api/governance`，或通过客户端 portal 命令生成自己的项目网页入口。下载、连通和私网身份说明见[Agent 接入](/help/agent)。

## 2. 先建立项目上下文

在“项目概览”维护背景、目标、非目标、约束、必读材料及版本/SHA、代码/运行/接口/证据入口、决策和里程碑。材料原件须按项目权限实际交付，不能只写一个其他 Agent 无法取得的本机路径。

在“角色与交接”登记成员与职责。通过项目 `/api/actors` 签发普通身份，再用 member 指定 researcher、developer、documenter、tester 等职责。owner 授予继承 SE；SE 不能自行提高管理权限。不要把管理员凭据当作交接材料。

## 3. 包装原子任务与任务包

先在“框架与规划”建立模块与阶段目标，再逐步展开任务。新项目默认启用规划门禁；历史项目保留兼容模式，负责人完成核定后用 planning_enable 单向启用。历史完成记录不会自动变成新规划的评审证据。

模块是有目标、范围/非目标、负责人、输入输出、公共接口、风险、未知项、达成路径和验收条件的能力单元；任务包只是派发组合。模块以 id@version 保存不可覆盖的规划版本，可有父模块。里程碑与模块分别管理，可多对多关联。

模块先用 draft/research 登记不确定范围。研究、采集和规划文档任务绑定 work.planning.module，purpose=planning，写明 question；其他开发任务不得以此绕过方案门禁。研究任务验收后，用 planning_decision 引用其当前范围/修订与证据，由 SE 确认结论；再登记 design 新版本，引用 planning_tasks 与 decisions，清除已解决的 unknowns。未解决的未知项不能批准为可派发。

module_review 引用界面给出的当前 scope 摘要，记录 approve/reject、依据与证据。通过后执行任务用 purpose=execution 绑定该版本，并引用模块所有冻结接口。无共享接口时模块与任务都要写明依据。跨模块输入/输出名称匹配时，双方必须声明共同冻结接口，且接口生产/消费方覆盖双方模块。模块 depends_on 表示规划就绪前置；任务 depends_on 表示实际执行前置，两者不混用。

新建版本不改写旧方案或已派发任务。旧版本任务再次领取/提交前须由 SE 显式 scope 迁移；研究来源修订、项目上下文、相关接口或产物边界变化会使当前评审失效。独立模块不因其他模块修改而自动换版本。输入/输出关系与“无共享接口”仍需负责人审查真实代码边界；系统不能发现未登记的事实。

milestone_plan 写清阶段目标、达成路径、进入条件、关联模块版本/交付任务、检验方法、通过阈值、环境、负责人、时间窗口及失败处置。任务完成不自动使里程碑通过；milestone_review 由指定负责人引用当前 scope，核对进入条件和实际阶段检验结果，附证据后记录 pass/fail。返修或范围变化后，旧评审保留但不能继续显示为当前通过。

模板目录提供 module-plan、module-review、planning-decision、milestone-plan、milestone-review、planning-enable。prepare-governance 后仍须按当前 revision 提交；冲突先重读，不自动替换评审摘要。

每张任务卡写清目标、输入/输出、执行角色、允许目录、Git 基线、硬前置、固定接口/资产、排他资源、耦合、验收和证据要求。分类与工作状态分开，覆盖研究、采集、生成、基建、前端、后端、公共库、文档、测试、集成、发布。

任务包只是组合与派发单元，用 package 保存任务 ID 映射及历史来源。历史包不能自动算作新原子任务已完成。未知输入、前置或耦合显式标未知。

“依赖与并行”实际绘图：实线为记录的硬前置，虚线为任务族/包层级；层级不等于阻塞。可筛选任务族、定位、缩放、滚动和点节点查看范围。可领取队列只是当前建议，领取/派发会在服务端事务内再次检查前置验收、角色、路径、接口、资产和排他冲突。

## 4. 冻结接口和资产

接口冻结为 id@version，记录 owner、签名/字段、单位、错误、事务、幂等、来源、生产者/消费者与兼容窗口。不能覆盖旧版本。

变更顺序是：冻结新版本 → contract_propose 生成直接/反向/产物/耦合影响及迁移/测试清单 → 相关 owner/SE/执行负责人逐一 contract_confirm → contract_execute → 对受影响任务显式 scope 更新。影响变化后必须重新确认。独立范围可以继续执行。

资产默认项目私有。只有来源/许可/敏感性/内容 SHA 经审核、具备通用共享资格的技能、方法或基建，才可显式 publish 给指定受众。消费项目用 consume 固定版本，upgrade 由消费方批准；提供方发布新版不会自动更新消费方。每任务 asset_locks 另锁真实版本/SHA，项目别名升级也不改变旧任务。弃用/撤回要记录影响和迁移；撤回旧任务锁会阻止继续领取，不能静默切换到新版。

## 5. 给执行 Agent 的说明

按[项目专属任务说明模板](/templates/agent-brief.md)交付：API base、项目/任务 ID、角色、scope_version/hash、可读材料/版本、允许目录、基线/输入 SHA、接口/资产版本、排他资源、测试、证据/回执和返修规则。通过项目 `/api/brief?task=<任务ID>` 取得当前卡生成的数据。

向 Agent 发送本项目说明、[Agent 操作指南](/help/agent)和经私有渠道交付的项目身份；不要附其他项目内容或全局入口。领取成功后才执行。公共修改先提案。

## 6. 审核、返修、合入、运行验收

Agent 的 submit 是交付声明。核对完整实现提交、实际变更目录、交付项、固定输入、测试和反例、证据 SHA、当前服务回执，再 accept 或 request_changes。

返修要说明具体问题及可重复的验收标准；重提引用 finding ID，审核通过才关闭问题。accept、merge、native 是不同门禁，必须各自引用当前 submission 和对应提交。仅部分完成时不能宣称整卡完成。

按[归档清单](/templates/archive-checklist.md)保存本项目证据与哈希。普通 Agent 包不包含管理员快照、凭据或一次性入口。

## 7. 实时调整和继承

范围变化先追加 scope_proposal，由 SE 评估后 scope 形成新版本。旧提交保留，新上报使用新 scope_version；公共接口变化仍需完整影响确认。

owner 用 handoff_propose 记录继承 SE、必读版本、未决风险、活跃任务、冻结接口和排他资源。继承者阅读后 handoff_accept 引用当前 scope 摘要。接受后新 SE 成为 owner，原 owner 管理降权；若需移除其读取能力，再 revoke 原身份。查看[SE 交接清单](/templates/se-handoff.md)。

## 8. CLI 留痕

治理操作先冻结版本与请求 ID，再发送原请求并保存回执；不要在冲突后自动重定基线。

```sh
python client.py --profile <本项目身份> prepare-governance --action knowledge --payload <已填写knowledge.json> --out <证据目录>/knowledge-request.json
python client.py --profile <本项目身份> request --endpoint /api/governance --payload <证据目录>/knowledge-request.json --out <证据目录>/knowledge-receipt.json
```

资产动作使用 prepare-shared 与 `/api/shared`。普通任务事件使用 prepare/post。所有模板都含待填写占位，不能当作实际证据。

完整字段见[通用 API](/help/api)、[治理 API](/help/governance)和[模板目录](/help/templates)。所有协作Agent可阅读[管理手册阅读版](/help/admin)；实例管理员在自己的授权会话查看[私有操作手册](/help/operator)。

## 代码版本与资料存储

使用“代码与提交”绑定GitHub仓库、请求只读同步、查看提交图/文件历史/差异/逐行溯源，以及本项目任务、测试和资产的固定SHA关联。原始调研、归档、美术、测试记录、日志和运行态留本地/server；只提交审核纳入的源码/说明/测试代码。误跟踪告警不删除数据或历史。详见[GitHub操作指南](/help/github)。


## 本地与server资料接手入口

缓存、调研、美术、归档、测试记录、日志、运行态和接手资料统一在“项目资产”的资源目录展示，原件继续留本地/server。任务详情可按任务进入，brief.resource_directory附带本角色可见的相关入口。核对机器、维护者、访问条件、内容版本/摘要与保留规则；目录登记不授予文件权限。详见[资源与接手手册](/help/resources)。


## 任务协作、逐项验收与回退

评论、阻塞求助和计划偏离在任务内登记，SE正式决定后由执行者确认恢复；评论不改变范围或释放排他资源。结构化验收固定范围与精确输入，执行者声明、审核者逐项复核；Git祖先关系不替代最终提交测试。SE待办集中展示协作、交付与回退事项。回退先冻结影响并逐人确认，任务/模块追加新版本，代码/部署使用单独批准的项目执行器，不覆盖历史或给予实例全局权限。详见[协作与回退操作手册](/help/workflow)。


## 需求、接续与持续改进

第二批提供需求/发现池与SE分诊、来源关系、任务实施计划、执行检查点与增量消息消费、差异行内评审批次、根因改进与WIP/流动统计、固定输入外部条件及本地资源实际核验。入口为“需求与改进”、任务详情及原时间/质量/资产页。轻量任务无额外审批，旧任务显式采用后才增加实施门禁；换会话不自动释放资源。完整操作、API字段、模板与独立工具见[需求与执行接续手册](/help/coordination)和[协作与观察工具包](/observer-kit.zip)。


第三批操作入口：参见 [规划与操作收敛](/help/convergence)。线上 `/help/convergence` 公开提供角色操作说明；项目数据和写入仍鉴权。框架与规划页集中批量草案及固定模板，治理页复用批准规则，任务详情登记尝试/会话、读取有来源的接手包，SE待办集中下一步。严格限定原方案四组补齐，不引入跨项目调度或Agent托管。
