01 · 本轮目标与边界

本轮明确只交付详细设计与页面原型。生产登录、项目权限、任务状态、执行器、既有验收和服务部署不作替换。只在公告板项目登记了四项待工程化需求，保留本次用户来源及“先设计”的决定。

需求预期结果本轮设计落点
项目 Token 用量知道消耗发生在哪个项目、阶段与任务，并知道哪些尚未采集时间与效率 → Token 用量；采集口径、覆盖率、归因与导出
真正的需求池核心目标、过程扩展、结项后想法统一收集，逐步工程化需求池、验收标准、承诺版本、变更记录及任务覆盖
缺陷管理从发现到复测关闭可追踪，问题不会因任务提交就被消失独立缺陷池、修复任务、目标版本、复测与重开
商用 UI/UX在高信息量下仍能快速定位、判断和操作分组导航、列表与详情、渐进表单、统一组件与完整状态

不在本轮扩展公司经营治理、计费与账单结算、员工绩效、外部聊天平台、自动 AI 决策或更换前端框架。页面的信息密度提高，不增加所有项目都必须采用的管理流程。

02 · 已有能力与真实差距

核对对象包括当前生产页面、项目源码及独立浏览器渲染。当前前端为原生 HTML/JavaScript/CSS，没有 Tailwind 或组件库；已有蓝色品牌令牌、字号与间距尺度，以及随系统变化的深色主题。新设计沿用这些基础，不引入新的构建依赖。

03 · 信息架构与角色路径

全局顶栏只放品牌、当前项目搜索、主题、身份和账户。项目选择始终可见；人类可跨授权项目切换，项目 SE 和 Worker 只能看到自己获准的项目。切换项目清空详情、选中项与未完成请求，筛选按用户及项目分别保存。

分组入口用户要回答的问题
工作空间项目概览、我的工作台项目要达成什么？我现在该处理什么？
产品管理需求池、缺陷池、需求变更为什么做？出现了什么问题？承诺改变了什么？
工程交付任务与验收、规划与依赖、测试与质量、代码与交付怎样实现、怎样并行、怎样证明和吸收？
协作与资源Agent 协作、项目资产、资料与里程碑谁在做？材料在哪里？背景和约束是什么？
分析与设置时间与效率、项目复盘、项目设置投入在哪里？哪里能优化？低频规则如何配置？

四条最常用路径

  1. 人类提出想法：选择项目 → 记录标题与问题 → 保存到想法 / 待评估，不强迫拆任务。
  2. SE 承诺实现：澄清目标与边界 → 确认可验证标准 → 选择里程碑 → 建立或关联原子任务与依赖。
  3. Worker 执行：我的工作台 → 可领取任务 → 原任务留言与交付 → 发现范围外问题时登记需求或缺陷；不用维护整个产品池。
  4. 质量与复盘：目标版本复测 → 缺陷关闭 / 重开 → 结合需求变化、返工与投入解释原因 → 提炼可复用方法。

SE 待办继续由事实和门禁生成，不要求模型重复解释所有快照。产品管理页解决产品决策，任务详情解决执行上下文；不能把两者做成重复表单。

04 · 需求池：允许渐进清晰，而不是待办堆积

需求是“谁在什么情境下，希望得到什么结果及为什么”，任务是实现它的执行单元。需求不要求预先工程化，也不等于承诺；优先级高并不表示本轮一定要做。

阶段最少信息可选补充不能自动推断
记录想法标题、问题 / 想法描述；项目、提出者、时间自动记录启动 / 过程 / 复盘 / 结项后来源，附件入口、标签不自动建立任务、批准预算或计入交付承诺
澄清与评估目标用户或使用情境、期望结果、范围 / 非目标、未决问题价值、优先级、约束、材料、调研任务、提出背景不因填写完整就判定正确；未知保留
确认与承诺版本化验收标准、负责人、明确决定及依据目标里程碑、方案、任务覆盖、适用治理规则确认需求与排期分开；未安排里程碑要显式标注
交付与验证任务 / 标准映射、当前成果和验证结论实际用户验证、缺陷、灰度或发布入口任务全 DONE 不代表需求业务目标自动达成
关闭与复盘达成 / 未达成 / 暂缓 / 不采纳的结论与原因实际投入、范围变化、经验与后续想法结项后新想法不覆盖原来已达成版本

状态与承诺分开

主路径：想法 / 待评估 → 待澄清 → 已确认 → 交付中 → 待业务验证 → 已达成 → 归档。页面可将“已确认且有排期”显示为“已承诺”，将任务运行事实显示为“执行中”，但后台分别保存需求决定、交付承诺与派生交付进度，避免人工维护三个互相冲突的状态。

旁路：暂缓、不采纳、重复。每种决定保留原因；重复指向规范需求且禁止成环，原讨论与来源不丢。重新考虑时追加决定，不删除以前的结论。结项仍可收集想法；真正处于只读归档的项目不能绕过权限写入，可由 owner 创建后续周期 / 项目并保留来源。

核心字段与列表

稳定 ID、标题、需求类型、提出阶段、提出者、负责人、目标、范围与非目标、优先级、承诺里程碑、验收项 ID、未决问题、来源材料、标签、关联任务、变更与讨论。列表默认只展示编号 / 标题、状态、优先级、类型、负责人、任务覆盖和更新时间；长描述、附件与审计记录放详情。

“未来想法”允许长期不细化。SE 每次只评估当前准备推进的一组，不为了管理格式把全部历史或未来需求都变成重审批流程。原型展示“确认 v1，暂不排期”，状态为“已确认”，交付仍是“待安排”；正式实现也必须单独保存承诺字段。

05 · 需求版本与变更：保留承诺，而不是直接改正文

未确认的草案可编辑并保存历史；确认后的需求定义与验收项形成不可变版本。修正文案、补充来源等低影响修改可以按 SE 已批准的规则快速处理，仍留差异记录；目标、范围、验收或接口变化必须成为正式变更提案。

  1. 提出：记录原版本、拟议差异、原因、提出者和时间；原版本继续有效。
  2. 评估：列出需求验收项、任务、模块、接口、测试、里程碑、资产消费者及当前执行者的直接与传递影响；未知明确为待调查，不当成零。
  3. 决定：授权 SE / owner 核对接受、暂缓、不采纳或要求调研，保留影响确认与迁移办法。
  4. 应用：确认新需求版本；受影响任务按原范围变更机制追加版本并通知执行者。若迁移尚未完成，显示“已批准 / 待工程核定”，不能假装新范围已经生效。
  5. 重验：仅对受影响的标准、运行与评审标注失效原因；无关模块和材料不被全量重审。当前作业是否继续仍按已确认的边界与 SE 决定执行。

同时存在多个变更时，目标版本和影响快照都要校验；409 展示当前版本与待提交差异，不静默覆盖、不自动重写请求 ID。可合并相关提案，但每个原来源仍保留。原型中的“费用结算”是未批准的新想法示例，不属于本轮 Token 统计范围。

06 · 缺陷：项目级问题，不是另一种任务

缺陷说明实际行为相对明确预期出现的偏差。缺陷可以先登记未知或不完整信息；“无法复现”与“已经修复”是不同结论。严重度记录影响，优先级记录处理顺序，两者独立。

时点记录内容门禁
发现摘要、实际现象、预期结果；提出者与时间信息不全仍可进入待分诊，不编造复现与根因
确认环境、版本、步骤、证据、影响、严重度、优先级、关联需求 / 用例按证据确认或转调查；重复缺陷指向规范对象并保留原报告
修复一个或多个修复任务、目标版本、计划回归范围按原任务治理领取 / 交付；提交不能自动关闭缺陷
复测真实版本、环境、用例 / 运行、结果、证据与复测者核对精确修复输入；原旧测试不能覆盖后续修改；高风险保留独立复核
关闭 / 重开关闭依据、例外处置或新的复现版本；保留各轮记录普通关闭必须通过复测；不修复 / 非缺陷为独立处置，不伪装通过

主路径：待分诊 → 待调查 / 已确认 → 已安排 → 修复中 → 待复测 → 已关闭；失败进入重开，可继续复用合适的修复任务或新建尝试，不覆盖旧证据。重复、不修复、非缺陷需要有权者给出理由；不能用这些状态绕过阻塞性 finding 的原审核门禁。

与现有评审发现的关系

任务 finding 继续用于当前交付审核，保持原稳定 ID、锚点和逐条处置。需要跨任务、跨版本或进入后续计划时，可以一次提升为缺陷并建立来源映射；重复提升返回同一缺陷。缺陷与 finding 的状态分别管理，双向展示事实但不自动互相关闭。测试失败也不自动成为缺陷：先区别预期失败、环境故障和真实产品偏差。

07 · 关联后续任务：把“为什么做”一直带到验证

需求 / 版本 / 验收项 ──覆盖──→ 模块与原子任务
       │                           │
       ├──变更提案──→ 影响与重新核定   ├──成果 / 实际输入 / 测试运行
       │                           │
       └──业务验证 ←──逐项复核───────┘

缺陷 ──修复任务──→ 修复版本 ──复测用例 / 证据──→ 关闭或重开
  ↑                                    │
评审发现 / 测试 / 用户反馈              └──同版本复盘

实际调用 / 会话 ──授权绑定──→ 项目 / 任务 / 阶段投入
                               ↓
                        需求变化、质量与效率复盘

一条需求可对应多个模块与任务；一个任务也可能覆盖多个需求标准，但每条映射要说明覆盖哪一项。关联只建立追踪关系，不静默修改任务范围、硬依赖或接口。任务创建向导从当前需求版本带入目标与标准草案，由 SE 核对执行边界；可以关联已有任务，避免重复建卡。

需求达成由每项标准的当前有效验证结论支持，再由有权者确认业务目标。未覆盖、验证失败、目标输入变化或必要缺陷未解决时显示差距。普通轻量需求可以只用一条标准、一个任务及适用的原验证，不强制新增独立测试执行器或额外实施审批。

任务详情新增紧凑的来源需求、标准与产品缺陷区块；需求详情给出覆盖矩阵、关联任务、测试与未决缺陷。点入任务再返回时保留列表筛选、排序、分页、滚动与选中项；项目切换后全部按新项目核对。

08 · Token 统计：按项目归属，先保证不会算错

页面与主指标

入口放在“时间与效率”，使用 Token 用量、时间与流动、优化与复盘三个局部视图。默认显示当前项目与周期的已知用量、采集范围、输入内的缓存占比、待归因用量；然后是趋势、阶段 / 模型 / 任务分布和可追溯明细。

指标定义防误读
已知 Token 合计规范化后的输入总量 + 输出总量，按唯一调用累计是已知下限；同一流式 / 最终结果、重放和导入不可重复相加
缓存与推理缓存读取 / 写入按供应商语义映射；推理细分保留来源已包含在输入或输出的部分不再加一次；未知细分不填 0
采集覆盖已登记且在统计范围内的会话：完整 / 部分 / 未接入；同时说明已报告调用数18 / 23 是演示的已关联会话范围，不代表账号全部会话或 78.3% 的真实消耗
待归因已知属于本项目，但没有可靠任务 / 阶段映射的记录包含在项目合计，单列原因；不按任务数平均摊分
项目级投入明确的 SE 协调、规划、项目研究等未绑定任务的合法投入与“归因失败”分开，不强行补一张任务卡
上下文占用 / 费用上下文压力属于当前请求状态；费用需独立计费依据不作为累计用量加总；本轮不把订阅额度或标价换算成实际账单

采集与归因路径

  1. 受管节点只采集本机被授权且有绑定归属的原生会话；项目由服务端绑定核对，不能靠 Agent 自填 project_id 获得跨项目记账能力。
  2. 规范化事件最少包含：项目、节点、运行时与适配器版本、原会话 / 调用标识、计数器 epoch、发生与接收时间、模型 / 路由、输入 / 输出、可选细分、来源类别及原件摘要。
  3. 绑定明确任务时固定 task / scope / attempt / 阶段；阶段按当时的执行上下文记录，不根据完成后的名称猜测。SE 项目协调保持项目级。项目归属不明先留在原节点 / 有权者的待核定入口，不读取或摊给其他项目。
  4. 非受管会话可由本机维护者按明确白名单导入；先给预览、来源与分段归属，再由有权者核定。不能默认扫描整台电脑所有会话。
  5. 只上传度量元数据与受控原件引用，不上传提示词、聊天正文、密钥或全部日志。原件留本地 / NAS，并在项目资产登记读取条件。

三种运行时的接入判断

Codex 官方协议提供线程用量更新，其中同时存在累计与最近一次统计。适配器应选择统一的来源和差分策略，不能把两份计数同时累计；实际安装版本还需独立核对。官方协议来源。

DeepSeek Harness 的官方 Token-meter 区分累计消耗、上下文压力与估算，并说明同次尝试的流式记录会被最终样本替代、重试需要单独计算。设计因此将“实际报告的消耗”和“当前上下文估计”分开，具体 SDK 暴露方式仍按部署版本验证。官方说明。

Zcode 当前已验证的控制面能驱动会话，但本轮没有验证其供应商用量字段与导出语义，不能声称已能准确采集。后续先用真实样本确认计数是单次、流式还是累计，再启用该适配器；不可用时显示未接入或人工导入的明确来源。原型的 Zcode 数字是刻意编写的导入示例。

09 · 复盘：把变化与结果转成下一次可用的经验

每次里程碑与结项记录一个可追溯的复盘快照：最初确认的需求版本、后续增加 / 删除 / 调整的范围、每次决定原因、目标达成情况、缺陷发生与复测、投入与等待、返工轮次、模型用量及记录覆盖。

要回答的问题数据与观察输出
为什么范围变大？核心 / 过程 / 结项后来源、承诺后的新增、变更前后差异哪些是目标细化，哪些是真扩展，哪些需要另起周期
哪里反复或排队？等待原因、需求澄清、评审队列、返工与交接可压缩环节及可验证的改进假设
质量在哪里损失？缺陷影响、发现阶段、重开与漏测、对应需求标准补用例、改接口、改材料或改检查清单
哪些投入可比较？同类型任务的实际投入与 Token，模型、工具、复用程度、记录完整度有样本与适用条件的估算参考，不做单一排名
什么能给其他项目用？经过核对的流程、模板、组件、自动测试、调查方法显式审核的不可变资产版本；不自动共享私有材料

小项目可以只写“事实、原因、下一次做法、如何验证”四项。改进保持假设与已验证结果的区别；不能因为记录了一条经验就声称其他项目会节省固定比例时间。

10 · 页面与交互规格

高密度工作台，而不是堆满字段

顶部 56px；项目侧栏约 232px，可收起并记忆用户偏好；主区从 1280px 起保持紧凑表格。主标题 24px，表格正文 14px、辅助信息 12px，字重 400 / 600。间距以既有 4 / 8 / 12 / 16 / 24 / 32 为主，单行行高基准 44px，双行信息约 64px，紧凑模式缩减行内垂直间距但不缩小文字。6px 为原型控件圆角提案，正式组件定稿时与当前令牌合并，不能形成两套互相竞争的样式。

一页只有一个主要动作：需求页“记录需求”、缺陷页“报告缺陷”、统计页“导出当前视图”。详情打开后背景不可交互，主动作变为当前对象的下一步；批量操作默认只支持安全、可回顾的标签 / 负责人调整，不能一键批准所有范围变更。

列表

  • 表头、列宽与行节奏统一；标题可换两行，编号为次级信息。状态同时有文字与语义色。
  • 筛选：状态、优先级、来源阶段、负责人、里程碑、标签；搜索说明“当前项目”。默认视图与已保存视图按人和项目隔离。
  • 排序、分页、列显隐与密度分开；生产采用服务端筛选与分页，搜索可取消旧请求，不能慢响应覆盖新条件。
  • 分页或后台更新不跳回顶部；有新数据时显示“有更新”，由用户刷新；当前正在编辑的表单不被轮询重绘。

详情与表单

  • 列表 + 680px 侧边详情；概述、关联交付、变更记录、讨论局部切换。可通过完整深链打开，并支持 Esc、焦点限制和关闭后回到原对象。
  • 快速登记只有业务必需字段；技术原件、证据哈希与完整审计在相关步骤渐进展开，不让人手写 JSON。
  • 新增、评估、提案、批准、验证使用不同语义的表单；有未保存内容时离开需提示，冲突保留已输入内容。
  • 最常用动作就地完成；长描述、复现步骤和评论避免超过约 65–75ch。数据表格不受段落宽度限制。

移动端

375px 起侧栏变抽屉，列表保留标题、编号与状态，次要列可隐藏或在受控表格容器内滚动；不让整个页面横向溢出。详情使用全屏面板，主要操作位于底部，触控目标至少 44px。图表提供文字 / 表格等价内容，不要求精确悬停才能读取。

主题与组件

浅色为首次默认，允许明确切换深色并记忆偏好；不因操作系统主题切换重置个人选择。沿用既有品牌色，只使用中性文字主 / 次 / 辅助三级。统一按钮、状态标签、优先级、工具条、数据表、分页、详情、对话框、时间线、提示和空状态。图标用于识别，不能替代标签或权限说明。

13 · 数据、兼容与旧入口映射

单一事实来源，不再建设平行待办池
